# 项目需求

本文件说明 dsh-superagent-wish 要满足 wish 的什么需求，以及这些需求落到插件上的现状。
需求编号见 `./REQUIREMENTS.md`，术语见仓库根目录 `GLOSSARY.md`，四层结构与检验标准见 `./spec/framework.md`。

---

## 一、这件事在做什么

这个插件用 DSH 实现一套人机协作模式：wish 只和 Partner 对话，Partner 负责沟通和派活，Secretary 过滤外部事件，Worker 负责分析和执行。

目标不是把活干得多快，而是让对话保持在可以深入的状态，同时不失去动手能力。原文的说法是“上下文薄，和人的交流才更深”：把执行移出对话上下文，模型才会把注意力放在与人交流上。

---

## 二、分工

分工的边界是：wish 决定做什么和怎么做，Partner 谈，Worker 做。

| 功能 | 职责方 | 说明 |
|---|---|---|
| 信息获取 | wish | wish 提供材料、事实和意图；Partner 不替 wish 收集材料 |
| 决策与动作选择 | wish | 判断权归 wish（R7） |
| 信息分析 | Worker | 启发者发散，执行者按 task spec 分析并产出 |
| 动作执行 | Worker | 写文件、跑命令、产出交付物 |
| 与人沟通 | Partner | 追问、直言、摆选项、呈报状态 |
| 派活 | Partner | 把对话收敛成 task spec 或 exploratory prompt，确认后派出 |
| 过滤外部事件 | Secretary | 文件和定时事件要不要开成工作单元 |
| 状态转换、队列、投递 | 插件代码 | 不改判断，只按固定规则执行 |

Partner 的上下文只围绕对话组织（R8）。这不表示 Partner 看不到原始信息：默认只拿结论；要更多细节时向工作单元追问（`partner_followup`），不读 Worker 会话。

## 四、已确认的架构对应

这些是从讨论中推出、wish 已确认的对应关系，作为架构参照，不是实现要求。

| 讨论中的概念 | 本插件的对应 |
|---|---|
| Router | Partner |
| Worker | 启发者、执行者 |
| 事件源 | 文件入口、定时巡查；wish 的消息由 Partner 直接接，不经事件源 |
| Mandate | 工作单元的授权：task spec 的 `scope`，追加输入并入 `scope`，原范围留在 `previousScopes` |
| Watchdog | 状态汇报与偏差处理 |

派活方式已定：Worker 自选 skill 与 MCP，同构 Worker 加事件流派发。

## 五、wish 的使用方式

wish 的使用方式是：讨论 → 确认 → 派出 → 整合带回；执行期间只在卡点时被打断。

1. wish 把碎片想法、判断、材料和问题交给 Partner。
2. Partner 追问意图，指出 wish 没想到的地方，把权重不同的选项并列摆出来。
3. Partner 复述并能被更正：主题、需求模型里哪条是原话、哪条是推断。
4. 需要发散时派启发者；方向确认后派执行者。
5. 派出前 Partner 说“我准备做 X，因为 Y，同意吗？”，wish 确认后才派出。
6. 执行期间只报卡点；wish 可以随时介入。
7. 结束时 Partner 整合两类结果带回，不转贴 Worker 原文。

## 六、插件承担的部分

协作模式由这个插件承载。每一条要么在插件里有对应实现，要么是已知缺口。

| 职责 | 内容 | 需求 | 现状 |
|---|---|---|---|
| 接话 | 追问、直言、并列选项、主题锚定、逐层共建需求 | R1–R12 | 行为规格已成文（`./spec/interaction-spec.md`），未写进提示词，无运行时检查 |
| 派活 | 建 Worker 会话、设权限、命名、送第一条消息，可在派发时指定模型 | R13、R14、R16 | 已实现。链路在真实桌面应用里跑通 |
| 回报 | Worker 用 `partner_report` 提交状态和摘要，经 `steer` 送进 Partner；无回报时补 `waiting` | R16、R17 | 已实现。来源为 `agent-message`（`form: 'relay'`），带发送方会话 id |
| 可介入 | 派出后追加消息、叫停 | R16、R30 | 已实现。`partner_followup` 追加，`partner_stop` 叫停当前一轮，工作单元保留 |
| 多任务 | 工作单元 / 输入 / 派工 / 授权表 | R15、R16、R30 | 已实现。表建在 `ctx.storageDomain` 上，重启后读回 |
| 外部入口 | 文件和定时事件由 Secretary 判断 | R23、R24、R29 | 已实现。`files` 与 `schedule` 两个事件源，`partner_decide` 把判断写回 |

剩下的缺口在对话行为本身：R1–R12 只有规格，还没进提示词。记忆层（R21、R22、Q3）与 Watchdog（Q4）在插件范围之外。

## 七、接话与低打扰

接话与打扰的行为写在行为规格里（`./spec/interaction-spec.md`）：

- 主题锚定：会话开头复述主题；延伸讨论后整合回主题，按新版本安排后续任务。
- 逐层共建需求：每次补充并进同一需求模型，每条标明原话或推断。
- 备齐判断材料：权威来源、现状（含缺口）、已确认意图、并列选项。wish 问到时才给意见。

低打扰针对执行过程，只汇报卡点。三种情形必须打断：Worker 将超出 task spec 的 `scope`；遇到产品决策或范围不清晰；工具失败且没有明显的替代路径。

这些做法目前没有写进 Partner 的提示词，也没有运行时检查；`partner.js` 的提示词只约定工作单元的派发与回报协议。

---

## 八、边界

这个插件的范围是四层结构里的运行时层。资产层（人工知识库、技能库、机器记忆）和能力层（浏览器操作、文档处理、记忆读写）在本机已存在，插件引用，不重建。

以下需求不在插件范围内，等对应的层接入后再谈：

| 需求 | 依赖 |
|---|---|
| R5、R21、R22、Q3 | 记忆层 |
| Q4 | Watchdog |

R23、R24 的文件入口本轮按“文件与定时各自成为事件源”纳入，不属于外部依赖。

wish 的消息由 Partner 直接接；文件入口和定时是事件源，外部事件由 Secretary 判断，Partner 不参与。
