# 工作单元与判断位置

重写 dsh-superagent-wish 的两条根决定：一个活是什么，判断放在哪。

**一个活是工作单元，不是一次会话。** 工作单元有自己的身份、状态、输入队列、派工记录和授权；Worker 会话只是它在一个时段的执行者。原型把这件事分成 Ticket / Input / Assignment / Mandate 四张表，本插件照做，字段按个人使用收窄。

**判断放在 Partner，机制放在代码。** 原型的主 Session 只做路由，判断分散在策略规则和 Worker 上。本插件的 Partner 要判断值不值得开活、派给谁、此刻要不要对 wish 说；状态转换、队列、投递、并发这些不需要理解语境的事留在代码里。

## Considered Options

- **照搬原型的 Router 定位**：原型刻意让主 Session 不做技术判断，团队场景里判断由规则和 Worker 承担。个人使用没有这张规则网，照搬会得到一个更快把活推出去、但不理解 wish 此刻在想什么的调度器。
- **判断全交给 Worker**：Worker 只看见自己那个工作单元，看不见别的活和 wish 当时的意图。它做的不是判断。
- **判断全交给代码**：需要理解语境的事写不成规则，最后只能写成一堆开关。
- **原样照搬四张表**：原型的订阅模型假设一条消息会被多个活收到，服务于 GitHub 和飞书的多线程。本插件只有 wish 一个来源，订阅简化为“工作单元挂在哪条对话上”。

## Consequences

- Partner 的上下文要有判断依据：工作单元的名字、类型、状态。这是“上下文薄”要付的代价，靠“只在 Partner 主动查时披露”控制。
- 状态转换全部在代码里，有测试。Partner 和秘书不经手状态：它们调用工具，转换仍由代码执行。
- 越界没有运行时拦截。两类 Worker 越界都靠自报 `blocked` 和 Partner 复核（ADR-0001）。
- 判断错在 Partner 身上，而 Partner 与 wish 在同一份对话里，错可以被看见和纠正。
