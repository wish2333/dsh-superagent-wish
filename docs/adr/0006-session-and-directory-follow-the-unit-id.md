# Worker 会话 id 与工作目录都由工作单元 id 派生

工作单元是活的身份，Worker 会话是它在一个时段的执行者。为了让两者不会彼此走散，会话 id 与工作目录都写成工作单元 id 的函数：会话 `superagent-wish-<工作单元 id>`，目录 `<Partner 会话目录>/superagent-wish/<工作单元 id>`。

于是同一个工作单元的每一轮都在同一个会话、同一个目录里；会话被外部删除时，按同一个 id 打开下一个，目录原样沿用；标题改了只重命名会话，目录不动。四次派发不会各自留下一个按标题命名的目录。

工作单元记录里存四项：`partnerSessionId`、`workerSessionId`、`directory`、`type`。存而不算，是因为已结束的工作单元在新会话里再问时也要找回同一个目录和同一个会话名；迁移或改名这类事只能读记录，不能重算。

## Considered Options

- **每次派发生成随机会话 id，目录按标题加随机后缀**：重写前 `dsh-superagent` 就是这么做。会话删掉后重建出来的目录和原来不同，已有交付物就散在两处；追问要么丢会话，要么找不到原目录。
- **按标题推导会话 id**：同一标题会复用该标题已占的会话，包括一个坏掉的会话；而且标题一改，目录跟着改名，已有引用全部失效。
- **状态机按 `unit.type` 推出 Worker 会话 id**：可以省一列，但状态机就从纯状态转换变成要知道命名规则；`type` 之外的名字变化（例如以后换前缀）也要改状态机。存进来更直接。

## Consequences

- 工作单元表因此有三列由派发方写入，状态机不碰它们。`working-units.js` 的 `dispatch` 只记录，不改写。
- 目录名带工作单元 id，人能一眼对上是哪个活；标题在会话列表里看。
- 会话 id 里出现 `unit-3` 这样的编号，只是命名规则，不是 Partner 引用活的方式：Partner 只认工作单元 id。
- 会话被删除后重建，`agent.cancel` 作用于同 id 的新会话；库里仍排着的输入在下一个派工开始前不会丢。
